# Approximate bistochastic EVD

`kevd.cu` is a CUDA, multi-GPU implementation of the eigenvalue
decomposition (EVD) post-processing step that follows ARPC-LM.
It consumes the ARPC-LM outputs (the `r x r` inverse Cholesky factor
`L^{-1}` and the length-`r` pivot set `S`) and approximates the EVD
of the bistochastic normalization of the rank-`r` kernel approximation.
Here `r` denotes the realized rank of the ARPC-LM approximation.

As in `arpclm.cu`, the `NM x NM` kernel matrix `K` and the `NM x r`
factor `F` are never formed: kernel entries `K(R,S)` are regenerated in
row panels on demand.

The code performs four streaming passes over the `NM` kernel rows,
separated by two dense `r x r` phases.
Each pass makes one sweep over the rows and regenerates the kernel
entries it needs; each dense phase works on small `r x r` matrices
while no streaming is taking place.

## What the code computes

Let `F = K(:,S) L^{-T}` be the partial Cholesky factor and
`Khat = F F^T` the rank-`r` approximation of `K`.
The code computes the EVD of

```
    P = Dtil^{-1} Khat Qtil^{-1} Khat Dtil^{-1}
```

where `Dtil` and `Qtil` are diagonal normalization matrices
that make `P` symmetric, positive semidefinite and bistochastic.
Only the leading `k_out` eigenpairs are wanted downstream, with
`k_out << r`.

Everything that depends on the `NM` dimension is written through `K(:,S)`
rather than `F`, which keeps `L^{-1}` out of the streaming phases.
As a result, `L^{-1}` appears only in the small dense operations.
Using `K(S,S)^{-1} = L^{-T} L^{-1}`, the code computes the following.

```
pass 1    c1   = K(:,S)^T 1                       (r-vec)
dense     p1   = K(S,S)^{-1} c1
pass 2    dtil = K(:,S) p1                        (NM-vec)
          cq   = K(:,S)^T dtil^{-1}               (r-vec)
          Atil = K(S,:) Dtil^{-2} K(:,S)          (r x r, SPD)
dense     pq   = K(S,S)^{-1} cq
dense 1   A    = L^{-1} Atil L^{-T}
          R    = chol(A)                          (A = R^T R)
          G    = R L^{-1}
pass 3    qtil = K(:,S) pq                        (NM-vec)
          Btil = K(S,:) Qtil^{-1} K(:,S)          (r x r, SPD)
dense 2   W    = G Btil G^T
          V, Lambda = evd(W)
          Z    = L^{-T} R^{-1} V[:, top k_out]    (r x k_out)
pass 4    U(R) = Dtil(R)^{-1} K(R,S) Z            (NM x k_out)
```

The matrix `B = L^{-1} Btil L^{-T}` is never formed.
This is because

```
W = R B R^T = (R L^{-1}) Btil (R L^{-1})^T = G Btil G^T
```

which allows us to retire both `L^{-1}` and `R` once `G` is formed.
This lets pass 3 and the eigensolver run without those two
matrices loaded in device memory (motivated below),
and is the main reason why the streaming passes and dense phases
are interleaved in this order.

## The kernel matrix

`K` is generated by a Gaussian kernel function with constant bandwidth
acting on a dataset of spatiotemporal samples.
Each sample index refers to a point in space-time; the kernel compares
two samples by taking the squared difference over a delay window of
`Nq` consecutive time samples.

The kernel matrix is never fully formed.
It is evaluated in `rblk x r` row panels by `compute_kblock`, reused
from `arpclm.cu`.
Given a block of rows `R`, the code computes `K(R,S)`
against the whole pivot set `S` in single precision.

## Program structure

The code is a single SPMD program with one MPI rank per GPU.
Each rank controls one GPU device, drives it through a private CUDA
stream, and communicates with the others through NCCL collectives.
MPI is used for the initial setup, the small broadcasts used to replicate
dense phase results (explained below), and the final gather of the output.

The dense phase employs the cuSOLVERMp and cuBLASMp libraries.
Both take the same NCCL communicator, but each needs its own process
grid object over it.
The ranks are arranged in a `Pr x Pc` grid, chosen as the
factorization of the rank count that is closest to a square grid.

## Data distribution

Two data layouts coexist across the `Ndevs` devices.

- **1D row block** for the `K(R,S)` row panels.
Device `j` is responsible for the global rows `[j*Nrows, (j+1)*Nrows)`
and regenerates row panels with all `r` columns local.
The per-row matvecs (`dtil`, `qtil`) and the row scalings can then
be performed locally, without the need for collectives.

- **2D block cyclic** for the `r x r` matrices.
Matrix `L^{-1}`, the two Gram matrices `Atil` and `Btil`, and every
dense intermediate down to `Z` are distributed in this layout because
this is what the cuSOLVERMp and cuBLASMp libraries require.
The employed block size `nb` is a run parameter; the general rule
is to take the largest `nb` that leaves about eight blocks per dimension,
so that the dense phase has blocks to spread while the streaming Gram,
which prefers large blocks, keeps most of its rate.

Quantities of relatively small size are replicated on all devices.
This includes the input state data and the pivot set `S`,
which every device needs in full to regenerate its own kernel rows;
the `NM`-vectors `dtil` and `qtil`; the small `r`-vectors.

### Bridging the layouts

Two mechanisms translate between the two distribution layouts,
and between them and the host.

- **Panel redistribution, device to device.**
The computation of the Gram matrices `Atil` and `Btil`
contracts a scaled row block `K(R,S)` into a block cyclic
`r x r` matrix.
This is performed by the distributed `cublasMpSyrk`, which cannot take
operands on two different grids.
As a result, each scaled row panel `K(R,S)` is first redistributed from the
row block layout into the block cyclic one, using `cublasMpGemr2D`.
The row block layout is expressed as a block cyclic descriptor of its
own over a second, `Ndevs x 1` grid, so the redistribute is a library
call and the code performs no explicit block cyclic index arithmetic.

- **The root bridge, through the host.**
Input matrix `L^{-1}` is read as one undistributed `r x r` matrix
on root (rank 0), and has to be put into the block cyclic layout.
Conversely, `p1`, `pq` and `Z` are computed block cyclic but must
then be replicated on all devices.
Both directions can be accomplished using the cuSOLVERMp scatter/gather
pair, which takes the descriptors the code already has:
rank 0's host buffer is scattered into the block cyclic tiles on the way in,
and the small results are gathered to rank 0 and broadcast on the way out.
A plain `AllGather` would not do for the outbound direction, since it
would return the block cyclic rows interleaved, requiring a local
reshuffling.
These crossings are infrequent and small compared to the dense phase,
which is what makes the host round trip acceptable.

## Input

The problem is defined by the input data file and a set of compile-time
parameters at the top of `main`; there are no command line arguments.

The code reads the two ARPC-LM outputs (the inverse Cholesky factor
and the pivot set) from HDF5 files,
along with the input dataset ARPC-LM was also run on.
The kernel function is defined by its bandwidth and delay window `Nq`,
as in ARPC-LM, and these must match the values used there.

Tunable code parameters include the number of devices, the number of
leading eigenpairs `k_out` to extract, the streaming panel height `rblk`,
and the block size `nb` of the block cyclic matrices.
In our runs, `rblk` was chosen on memory grounds alone,
while `nb` follows the rule explained above.
The number of devices `Ndevs` must divide the number of samples,
and `rblk` must divide the per-device row count.

Two debug parameters are available: one enables the dumping of
intermediate results for validation against reference results;
the other reports per-GPU memory usage at a few chosen points
in the code.

## Output

The code writes one HDF5 file, containing

- all `r` eigenvalues, in double precision, in ascending order;
- the `NM x k_out` matrix of leading eigenvectors `U`, in single
  precision, flattened in row major order.
  Before flattening, the eigenvectors are also in ascending order,
  so the last extracted column corresponds to the leading eigenvector,
  and similarly for the rest.

The eigenvectors are assembled on rank 0 by an MPI gather of the
per-device row blocks.

## CUDA kernels

- `compute_kblock` — evaluate a row major kernel panel `K(R,S)`.
- `accum_colsums` — accumulate a panel's column sums into `c1`.
- `recip_float`, `rsqrt_float` — the elementwise `dtil^{-1}` and
  `qtil^{-1/2}` row weights.
- `scale_cast_panel` — apply a row weight to the float kernel panel and
  cast it into the double, column major source of the redistribute.
- `scale_rows_rm` — apply the row weight to the output panel in pass 4.

Everything else is left to cuBLAS for the local dense work and to
cuBLASMp and cuSOLVERMp for the distributed dense work.

## The computation phases

**Pass 1 — `c1`.** For each panel, regenerate `K(R,S)`, contract it
against the all-ones vector and accumulate the column sums into `c1`.
`AllReduce(c1)` at the end of the sweep makes it replicated.

*Dense:* `p1 = L^{-T}(L^{-1} c1)`, as two distributed triangular
products with a single column right hand side, returned replicated
through the root bridge.

**Pass 2 — `dtil`, `cq`, `Atil`.** For each panel:

1. `dtil(R) = K(R,S) p1`, a local matvec since `p1` is replicated.
2. Check `min(dtil(R)) > 0`.
3. Accumulate `cq += K(R,S)^T dtil(R)^{-1}`.
4. Row-scale and cast the panel to
   `Ktil(R,S) = diag(dtil(R)^{-1}) K(R,S)`,
   redistribute it to block cyclic, and accumulate
   `Atil += Ktil^T Ktil` with an accumulating distributed `syrk`.

At the end of the sweep: `AllGather(dtil)` and `AllReduce(cq)`.

*Dense:* `pq = L^{-T}(L^{-1} cq)`, exactly as `p1`.

**Dense phase 1.** On the block cyclic tiles:

1. Zero-fill the strict upper triangle of `L^{-1}`.
2. `T = L^{-1} Atil`, then `A = T L^{-T}`; `Atil` is released.
3. `R = chol(A)`, in place.
4. `G = R L^{-1}`, into the slot `T` occupied.
5. Spill `L^{-1}` and `R` to each rank's host memory; neither is read
   again until `Z`.

**Pass 3 — `qtil`, `Btil`.**
Analogous structure to that of pass 2.
For each panel:

1. `qtil(R) = K(R,S) pq` locally.
2. Check `min(qtil(R)) > 0`.
3. Row-scale and cast
   `Ktil(R,S) = diag(qtil(R)^{-1/2}) K(R,S)`,
   redistribute into block cyclic, and accumulate
   `Btil += Ktil^T Ktil` using `syrk`.
   `Btil` is stored in one of the tiles freed by the spills at the end of
   dense 1, and the whole panel path is reused from pass 2.

At the end of the sweep: `AllGather(qtil)`.

**Dense phase 2.**

1. `T = G Btil`, then `W = T G^T`; `Btil` and `G` are released.
2. `V, Lambda = syevd(W)`, all `r` eigenpairs.
3. Extract `Vk`, the trailing `k_out` columns of `V`; release `W`
   and `V`.
4. Restore `L^{-1}` and `R` from the host.
5. `Z = L^{-T}(R^{-1} Vk)`, as a triangular solve followed by a
   triangular product, then returned replicated through the root bridge.

**Pass 4 — emit `U`.**
For each panel: regenerate `K(R,S)`,
form `U(R) = diag(dtil(R)^{-1}) K(R,S) Z` locally
(since `Z` is replicated and `dtil` covers this device's own rows),
and copy the result to the controlling host.
The per-rank blocks are gathered to rank 0 and written at the end.

**Collectives.**
One `AllReduce` in pass 1, an `AllGather` and an `AllReduce` in pass 2,
an `AllGather` in pass 3, and the final gather of `U`;
plus the three small root-bridge gathers and broadcasts that return
`p1`, `pq` and `Z`.
Within the streaming loops there is only the per-panel redistribute.
The distributed dense calls communicate internally.

## Design choices

- **Pass ordering.**
  The order of the computation phases is influenced by memory demand.
  An `r x r` tile in double precision is the largest buffer in the code,
  so the work is arranged to hold as few of them as possible at the
  same time.
  Pass 3 takes place after dense phase 1 so that `Atil` and `Btil`
  never coexist in memory.
  In addition, forming `G = R L^{-1}` retires both `L^{-1}` and `R`,
  so both are spilled to the host before `Btil` is formed.
  The part of the code from the formation of `Btil` through the
  eigensolver `syevd` runs on three `r x r` tiles.
  During the eigensolver call, there are two live `r x r` tiles, plus
  the extra four tiles required as temporary workspace by the solver.
  This brings the total to 6 `r x r` double tiles, which is the
  peak memory demand of the algorithm.
  Spilling `L^{-1}` and `R` to the host and releasing additional
  buffers right before the `syevd` call is done to maintain the
  smallest possible memory peak.
- **Buffer reuse.**
  For the same reason as above, `r x r` buffers are reused and
  are not tied to one matrix.
  `Atil`'s slot becomes `Btil` and then eigensolver scratch,
  and `L^{-1}`'s becomes the eigenvector matrix.
  Buffers are otherwise freed when they are no longer needed.
- **Gram multiplication.**
  The Gram matrices `Atil` and `Btil` are computed using
  distributed `syrk`, which fills only one of their triangles
  (upper or lower), leaving the rest of the matrix undefined.
  Using general matrix multiplication to compute
  `A = L^{-1} Atil L^{-T}` and `W = G Btil G^T`
  would also read the undefined entries of `Atil` and `Btil`.
  This would require first updating the undefined entries with
  their symmetric defined ones, necessitating the use of a transpose
  across devices, since the two triangles of each matrix generally
  live on different devices.
  To avoid that, we use `symm` to perform the multiplications,
  which reads only one triangle of its symmetric operand.
  Taking each Gram matrix as `symm`'s symmetric operand leaves the
  undefined triangle untouched.
  The price is that `symm` reads its other operand in full, so the
  entries of `L^{-1}` above the diagonal must be set to zero first,
  which is achieved by the single `Laset` call.
- **Mixed precision.**
  Both single and double precision is used in the code.
  The kernel streaming work is done in single precision, which
  includes the kernel entries regeneration, row scaling, 
  the `dtil` and `qtil` matvecs, and the output `U`.
  On the other hand, all dense phase computations, the Gram matrix
  accumulators, and the cross-panel sums `c1` and `cq` are performed
  in double precision.
- **Regularized Cholesky.**
  To form `R = chol(A)` in dense phase 1 we compute the Cholesky
  decomposition of the regularized matrix `A + sI`, with `s`
  proportional to machine epsilon times `tr(A)`.
  This is done because forming `A = (Dtil^{-1} F)^T Dtil^{-1} F`
  squares the condition number of `Dtil^{-1} F`, potentially making
  the Cholesky decomposition numerically unstable.
- **Eigensolver output.**
  The eigensolver `syevd` computes all `r` eigenpairs of the input matrix.
  At the time of writing, cuSOLVERMp does not expose a subset eigensolver.
  As a result, we compute the full `r x r` eigenvector matrix instead
  of just the leading `k_out` eigenvectors actually wanted.
- **Dominant streaming cost.**
  The accumulation used to compute the Gram matrices `Atil` and `Btil`
  determines the asymptotic streaming cost.
  More specifically, kernel regeneration is `O(NM r Nq)` in float,
  while the Gram accumulation is `O(NM r^2)` in double.
  On hardware where the two compute rates are comparable,
  the Gram cost dominates for all rank values of interest.

## Build and run

The used compile and run commands are in the comment header of
`kevd.cu`.
They depend on the hardware and available library paths.

The code requires **cuBLASMp >= 0.9.1** and **cuSOLVERMp >= 0.8.0**.
This is because the symmetric and triangular products used in the dense
phases were introduced in cuBLASMp 0.9.0 and corrected on submatrix operands
in 0.9.1, and the distributed zero-fill was introduced in cuSOLVERMp 0.8.0.

The number of MPI ranks used to run the code must be equal to the
compile-time constant `Ndevs` set in the code.
